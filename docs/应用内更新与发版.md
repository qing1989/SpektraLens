# 应用内更新与发版

应用通过「关于 → 检查更新」发起联网，不在启动时自动请求。网络只用于版本清单和 APK 下载，不上传照片，不发送设备标识、账号或遥测。User-Agent 为 `SpektraLens/{versionName}`。不使用 GitHub API 或更新 SDK。

固定清单地址：
`https://github.com/qing1989/SpektraLens/releases/latest/download/latest.json`

发布页兜底：`https://github.com/qing1989/SpektraLens/releases/latest`。

## 发布步骤

**每次发版只有一件事不能漏：`SpektraLens-v{version}.apk` 和 `latest.json` 必须挂在同一个 Release 上。** 缺清单时固定地址返回 404，老版本点「检查更新」只会看到「暂时无法检查更新」，链路等于没上线（v0.3.9 即如此）。发完按下面的清单逐项确认，不要以「APK 已上传」当作完成。

1. 到下一版本正式发布时再递增 Gradle 的 versionName / versionCode。本功能开发仍保留 0.3.9 / 18。
2. 使用与已有渠道安装包**完全相同的签名密钥**生成 APK。曾发布 debug 签名包的渠道也必须沿用原密钥；不能用一把新 release 密钥覆盖它。妥善备份原密钥，不提交到仓库。代码无法改变 Android 的签名校验规则。
3. `scripts/package.py` 仍验证并复制既有 debug 构建，生成源码、交付包和 `deliverables/latest.json`。默认清单哈希来自该 debug APK，URL 仍使用正式资源名 `SpektraLens-v{version}.apk`，没有 debug 后缀。若实际发行另一个已签名 APK，使用 `python3 scripts/package.py --release-apk /path/to/signed.apk` 生成对应清单；此参数不会替代现有 debug 交付物。发布前确认 APK 内版本与当前 Gradle 版本一致。
4. 校对 latest.json 的 versionCode、versionName、SHA-256、sizeBytes、minSdk 与实际发布 APK 一致。可加入纯文本 releaseNotes 和按优先级排列的 HTTPS apkUrlMirrors；镜像必须是同一 APK。不要手填另一份包的哈希。
5. 创建 `v{version}` GitHub Release，将实际发行 APK 命名为 **`SpektraLens-v{version}.apk`**，与固定文件名 **`latest.json`** 一起上传；确认该 Release 被标记为 latest。清单 URL 为 `https://github.com/qing1989/SpektraLens/releases/download/v{version}/SpektraLens-v{version}.apk`。两个资产必须在同一个 Release：只挂 APK 会让 `releases/latest/download/latest.json` 返回 404。
6. 下载 Release 两个资源重新核对 SHA-256、大小、版本和签名。用已安装的上一版本真机测试检查、取消、下载、授权返回和系统安装确认；确认覆盖安装后照片、编辑记录和设置仍在。覆盖安装无需清数据或卸载。

发版后自检：

- [ ] Release 资产恰好包含 `SpektraLens-v{version}.apk` 与 `latest.json`，且该 Release 是 latest
- [ ] `latest.json` 的 versionCode / versionName / sha256 / sizeBytes / minSdk 与 APK 实际一致（哈希错会让用户下完就被自己的校验拒绝）
- [ ] 清单里的 `apkUrl` 指向本次 Release 的真实下载地址，镜像（若有）是同一份 APK
- [ ] 用上一版本安装包实测：能查到新版本、能下载、能完成一次真实覆盖安装

清单必需字段：整数 versionCode、字符串 versionName、HTTPS apkUrl、小写 64 位 hex sha256。建议正整数 sizeBytes；可选整数 minSdk、字符串 releaseNotes、字符串数组 apkUrlMirrors。缺少 sizeBytes 时采用 512 MiB 硬上限；缺少 minSdk 不额外限制；缺少说明显示默认文案，缺少镜像仅尝试主地址。无效镜像忽略，关键字段无效则拒绝更新。清单最大 64 KiB，APK 最大 512 MiB，重定向最多五次且每一跳必须 HTTPS，连接/读取超时 15/20 秒。每次检查与下载由用户发起，失败可打开发布页。

## 安装与生命周期

APK 只写应用私有 `cache/updates/{随机名}.apk`，每次候选源下载完成必须通过 SHA-256 校验；失败删除并尝试下一源，全部失败说明错误。下载支持取消，退出 Activity 时取消任务并清理缓存；系统可能回收缓存，安装前会再次校验，不存在的包不能安装。

首次安装更新需用户在系统设置授权「安装未知应用」。待安装哈希与缓存文件名保存在私有 preferences，返回后只续接一次；进程被回收后重建也可续接。返回时权限仍未授予，不再次跳设置，而是提示「尚未允许安装」并给出「重试」（复用已校验的缓存包，不重新下载）或「稍后」（删除该包，不留孤儿文件）。校验通过后使用 PackageInstaller.Session，API 31+ 明确要求用户操作；API 35 使用显式、可变 PendingIntent 接收安装结果，并通过 ActivityOptions 显式授予该回调所需的启动权限，再打开系统确认界面。不暴露 APK URI，不修改 ShareProvider。

## 验证

`python3 scripts/test_updates.py`：JDK 17+，无 Android SDK 或第三方测试依赖，测试清单解析、安全缺省、无效字段、版本号比较、镜像过滤与真实文件哈希。Android 环境也可运行 `./gradlew :app:testUpdatePolicy`。

Android 回归可使用 `python3 scripts/device_tests.py --test-update-install`，要求只连接一个模拟器。常规测试使用进程内 HTTP 响应夹具，覆盖固定清单地址、HTTPS 重定向、流量上限、截断、取消、镜像回退和哈希拒绝；测试不会访问外部更新服务器。最后单独运行系统安装确认测试，使用已安装的同签名 APK 作为夹具，仅打开并取消确认界面。脚本在测试进程外配置、恢复「安装未知应用」权限，因为撤销该权限可能使 Android 结束应用进程。普通 `device_tests.py` 不运行这项需要授权的系统界面测试。

2026-11-11 的 Android 15 验证发现，缺少 PendingIntent 创建方启动选项时，系统会记录 `Background activity launch blocked`，无法正常打开安装确认页。对应修复遵循 [Android 的 PendingIntent 启动规则](https://developer.android.com/guide/components/activities/secure-bal#creators-must-opt-in-for-pendingintent)，仅作用于专用的安装状态回调。

2026-11-12 在当前 `feature/in-app-update` 上复核安装权限链路（保留版本 `0.4.0 / 19` 的调试构建，Android 15 / API 35 arm64 模拟器）：

- `appops set app.spektrafilm REQUEST_INSTALL_PACKAGES deny` 后 `UpdateInstrumentedTest`：8 项通过，含「校验通过但未授权时弹出『允许安装更新』」与「从设置返回仍未授权时复用缓存包并给出重试」。
- 恢复 `allow` 后 `UpdateInstallInstrumentedTest`：1 项通过，系统确认页正常弹出并取消；截图可见 Package Installer 的 CANCEL / UPDATE，logcat 无 `Background activity launch blocked`。测试后权限恢复为 `default`。
