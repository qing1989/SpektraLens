## 2026-11-19 · 导入弹窗首屏闪烁修复（源码）

- 现象：0.5.0 用户反馈点击导入照片后，照片选择弹窗前几行会闪烁；多进几次后不再明显。
- 原因：GallerySheet 是 Dialog，默认窗口进入动画先于 show() 后的透明背景和尺寸设置执行，面板会以半透明状态压在家页面上；首次打开时 MediaStore/缩略图缓存是冷的，首行数据和图片可能在动画期间才到达，放大了闪烁。次因是 Tile.bind() 对同一个 key 也会取消在途缩略图请求并清空 ImageView，选中或分页触发的 notifyDataSetChanged() 会让可见 tile 重载。
- 改动：
  - GallerySheet.show() 在 super.show() 前完成窗口背景、重力、dim、窗口动画和尺寸设置；关闭默认窗口动画，改为 root 的 180ms 上滑，只做 translationY，不做整窗 alpha。
  - Tile.bind() 增加同 key 幂等：同 key 且已有缓存或正在加载时只更新选中态，不取消请求、不清空图片；换 key 才取消旧请求并清空。
  - Tile.startLoad() 用 request 身份校验回调，避免旧请求覆盖新 tile；取消或失败时结束 loading。
- 关键文件：android/app/src/main/java/app/spektrafilm/GallerySheet.java。
- 验证：/usr/bin/python3 scripts/build.py --offline :app:compileDebugJavaWithJavac :app:compileDebugAndroidTestJavaWithJavac :app:testLibraryPolicy :app:testFilmStockPolicy :app:testUpdatePolicy :app:testThumbnailPolicy :app:testGalleryPaging :app:lintDebug 通过；图库 35、胶片 571、更新 57、缩略图 48、分页 65，共 776 项；lint 0 错误、8 项既有警告，无 GallerySheet 新增。

## 2026-11-18 · 导入弹窗超大相册（源码）

- 触发：小米 15 系统相册近万张照片，点击「开始导入照片」后 GallerySheet 长期停在「正在读取相册…」（用户截图）。
- 原因判断：`GalleryPhotos.query` 在 8 个元数据列之外同时取 `MediaStore.MediaColumns.XMP` 并对每行 `getString` / `getBlob`；厂商 Provider 的 XMP 通常是多 KB 的 JSON，10,000 行会触发大量 CursorWindow 重填，查询被拖到分钟级。
- 修复：列表只取轻量元数据；每页 400 行（Android 11+ 使用 `QUERY_ARG_LIMIT` / `QUERY_ARG_OFFSET`），首页到达立即上屏，后台继续追加。`GalleryPaging` 处理短页、空页、厂商无视 limit（返回行数大于页长即视为已返回全部）和无视 offset（整页重复则回退一次全量查询）；整页均为不支持格式时继续下一页。分页参数抛异常时退回一次性查询。
- Live / Motion Photo：XMP 改为点选时单行查询（`_id = ?`），命中立即取消勾选并提示；复制完成后 `PhotoFormats.isMovingPhoto` 的头尾字节扫描保持不变。
- 测试：新增 JVM `GalleryPagingTest`（65 项，含 10,000 张 26 次分页、重复页回退、全不支持页继续、非法页长）；新增 instrumentation `GalleryLargeLibraryInstrumentedTest`（12,000 行假 Provider：列表不得请求 XMP 列、第二页与第一页不重复、策略可走完整库、单行 XMP 探针只读 1 行）。
- 结果：主代码与 instrumentation 源码编译通过；`testLibraryPolicy`（35 项）、`testFilmStockPolicy`（571 项）、`testUpdatePolicy`（57 项）、`testThumbnailPolicy`（48 项）、`testGalleryPaging`（65 项）与 `lintDebug`（0 错误、6 项既有警告）通过。

## RAW 与原尺寸证据

1. 合成 DNG：256 × 192，单 Bayer CFA IFD，没有 JPEG、缩略图或第二预览 IFD。Android 上通过 LibRaw 得到 128 × 96 预览，再从传感器数据重新解码并导出 256 × 192 PNG16。独立 TIFF 解析确认输入只有 CFA 图像，证明没有拿内嵌预览替代 RAW 解码。
2. 真实相机：rawpy 固定 commit 测试目录中的 Nikon D3S `iss030e122639.NEF`。元数据读出 Nikon / D3S、ISO 3200、28 mm、f/1.4；384 像素预览与真实光谱显影均通过。另一次从原文件解码后，实际导出 **4284 × 2844 JPEG**，与 LibRaw 识别的原始有效尺寸一致。
3. 3072 × 2048 合成输入实际光谱显影并导出 3072 × 2048 PNG16，证明没有沿用 2560 上限。

真实相机样片只作本地验证，未包含在 APK 或源码 ZIP 中；来源、固定 commit 与校验值写入 `scripts/device_tests.py`。这一项不能证明所有 `.RAF`、`.ARW`、`.CR3` 等机型均可用。

## 输出文件独立校验

从应用私有目录取出实际导出文件，使用独立 Python/Pillow/tifffile/标准 PNG 解析验证：

- 相同显影与编辑参数导出的 PNG16、TIFF16，解码后 RGB 样本 **逐像素完全一致**。
- PNG 所有 chunk CRC 通过；IHDR 标明每通道 16 位、RGB。TIFF 的 BitsPerSample 为 16，含 ICC；JPEG 含 sRGB ICC。
- 3072 × 2048 PNG 的 99.60% 通道样本低 8 位非零，确认不是把 8 位结果简单乘 257 后包装成 16 位。
- 在相同输入尺寸下，PNG16 转成屏幕 8 位后的像素与实际编辑预览每通道差值不超过 1。

该预览一致性断言使用同尺寸、关闭随机质感的输入。不同分辨率下的采样、颗粒和光晕可以有差异，未声称低分辨率预览与原尺寸结果逐像素相同。

# v0.2.2 引擎启动、独立进程与 CPU 兼容显影

验证日期：2026-11-01（Asia/Shanghai）。用户诊断设备为 OPPO PLP110 / Android API 37；10,716,747 字节 `84.jpg` 在 200 ms 内完成读取及保存，引擎仍显示准备中或不可用。由此确认等待发生于后续引擎阶段；旧版没有逐调用初始化日志，不能据此断言具体阻塞在哪次厂商 Vulkan 调用。

## 改动

- 编辑器、GPU 显影和 CPU 兼容显影分别运行于独立进程。GPU 启动超时或异常会结束该进程并尝试兼容显影；OPPO PLP110 且 API >= 37 的自动模式直接使用 CPU。
- CPU 库来自固定 SwiftShader 源码，在本机执行相同光谱 SPIR-V；保留 math guard、数值编译设置、测量数据和原始着色器，没有以简单滤镜代替显影。
- 初始化阶段、自检、设备/驱动、PID、回退原因写入可复制诊断。初始化和 RPC 各有期限，失败提供重启入口。预览进程退出不会清空编辑器内的照片或参数。
- 关闭连接先解绑，再结束子进程；后续连接等待旧 Binder 死亡。处理 Activity 快速重建遗留会话，连续重试不能复用已初始化的旧引擎。主 Activity 复用已有任务，分享输入无需等待引擎就绪即可读取普通照片。
- 细节、固定源码和重建命令见 `兼容显影实现.md`。上游 SpektraLab 文件与 SwiftShader 源文件均保持原字节，适配由 Android 层和构建参数完成。

- 原生处理库启用严格浮点条件下的 `-O2`，LibRaw 保持原编译方式。对照基准的 JPEG 文件哈希一致；14 份既有编辑导出文件（含真实 NEF 和测试 DNG）与优化前逐字节一致。81 项随包 CPU 库、着色器、材料和授权 PNG 保持原字节，两份 `libspektra.so` 因编译优化及计时更新。
- 完整原生/RAW/导出/恢复/界面测试 **38 项通过，70.473 秒**；新增图库后，图库权限、照片 ID 映射、滑块、首页比例、导入隔离和胶片图标共 **13 项通过，14.732 秒**。两组有10项重叠，合计覆盖41个不同测试。最终构建与 Lint 通过。

- 手机图库采用底部三列网格，真实系统相册按时间倒序；拖动把手展开/收起、相册选择、应用照片切换、文件入口、点图进入编辑与返回首页均检查通过。仅列照片，没有拍照或视频格子。

- 查询与缩略图不使用显影队列；缩略图并发3、缓存12MiB，关闭时取消请求并释放列表与缓存。全部/部分/拒绝权限区分、拒绝前不查询媒体、三列尺寸及照片点击 ID 映射有设备断言。

# 2026-11-17：黑白胶片、银盐相纸与 CineStill 800T 接入

验证日期：2026-11-17（Asia/Shanghai）。从固定上游 SpektraLab `267ee24380091e5bee87658d00f6c33d77321194` 接入 Kodak Tri-X 400、Kodak T-Max 100、Fujifilm Neopan 100 Acros II、Ilford HP5 Plus 400 四款黑白胶片、Ilford Multigrade IV RC 可变反差银盐相纸与 CineStill 800T。当前资源为 25 款胶片、9 款印相材料。

## 行为与数据约束

- `FilmStockPolicy` 统一生成主预览、画廊缩略图和导出的黑白覆盖参数。黑白固定使用银盐相纸、关闭彩色亚层颗粒与扩展动态范围，并按上游 2 号反差使用 C/M/Y `0/0/68`；彩色滤镜位移清零。
- 黑白相纸自动联动，切换胶片、撤销、重做及恢复照片时都会再次校正，不能混入彩色相纸；切回彩色时自动恢复合法彩色相纸及原有彩色滤色编辑。
- 默认强度对应上游颗粒校准：Tri-X `1.70`、T-Max `0.74`、Acros II `0.64`、HP5 `1.49`。高于 1 的胶片在滑块高段重新映射，仍在 0～2 的引擎上限内逐级变化。
- 编辑器新增“黑白”分类；黑白胶片页提供无 / 黄 / 橙 / 红 / 绿 / 蓝六项滤镜。相纸页把上游七个整档与半档压缩为低、较低、标准、较高、高五档，右侧只显示当前档位效果说明。横向档位条与胶片画廊一致，点中间项不位移，只有点当前视口边缘且外侧还有选项时滑一格；面板重建后选中项保持可见。
- 黑白只有一款相纸时隐藏无意义的相纸选择按钮，并隐藏彩色印相的洋红 / 黄色滤色滑块。CineStill 800T 在“质感”页显示 0～8 EV、默认 4.0 EV 的高光余量，其他胶片不发送该参数。
- 新增产品配置追加在原目录末尾，`fujifilm_c200` 仍是 0.4.6 的「全部」首项和导入默认胶片。25 款标签均由项目 Canvas 代码绘制，没有加入第三方胶卷 PNG；产品配置字节、署名和原始 NOTICE 随 APK 许可证资源保留。
