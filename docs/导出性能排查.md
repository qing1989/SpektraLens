# v0.3.1 导出性能排查

2026-11-03，针对 OPPO PLP110 / API 37 上十几 MB JPEG 原尺寸导出耗时较长的反馈。

## 已确认的原因

交付的是可直接安装的 Debug APK，原生 CMake 的实际编译命令没有 `-O` 优化级别，等同 `-O0`。这影响 CPU 上执行的扫描调色、几何采样、像素转换和 stb JPEG 编码；使用 GPU 显影仍然需要这些阶段。源码中配置 GPU 并不表示所有导出工作都在 GPU 上。

`CMakeLists.txt` 为 `spektra` 增加 `-O2 -fno-fast-math -ffp-contract=off`，保留 Debug、GPU 自检与原先数值约束。此次只优化客户端原生处理库；LibRaw 沿用既有编译方式，以保留 RAW 解码输出。材料模型、35 个 SPIR-V、随包 SwiftShader 均未修改。

## 同图前后测量

Android 15 / API 35 arm64 模拟器；GPU 使用模拟器的 SwiftShader，不是 OPPO 的物理 GPU。固定输入为 4000×3000 的 JPEG，12,185,409 字节，输入质量 95、输出维持原有质量 96。使用 Portra 400 与 Endura，开启基础调色，关闭颗粒、光晕和炫光，以隔离基础显影及编码开销。每版均重新解码原文件，执行两次原尺寸导出，未复用预览像素或缓存结果；下表为两次平均。正式基准时没有并行编译，最初与编译重叠的基线已弃用。

| 阶段 | 优化前 | 优化后 |
|---|---|---|
| 原文件解码与输入 | 0.756 秒 | 0.651 秒 |
| 光谱显影 | 6.540 秒 | 6.174 秒 |
| 扫描调色与几何 | 3.250 秒 | 0.658 秒 |
| JPEG 编码与缓存写入 | 6.416 秒 | 0.503 秒 |
| 全过程 | 17.176 秒 | 8.007 秒 |

总时间下降约 53.4%，约为原先的 2.15 倍速度。这个合成噪声输入用于可重复性能测试，不代表所有实际照片；这组编码后文件和源文件的 SHA-256 在前后四次测量中完全一致。两轮单项耗时、源文件哈希、后端和结果见交付包 `verification/v0.3.1/performance-*.json` 与 `baseline-timings-idle.json`。

另测 1600×1200、1,948,719 字节 JPEG，开启颗粒、光晕、炫光并执行同样调色，两次平均从 3.638 秒降到 2.254 秒，文件哈希同样一致。两组均未触发回退。

## 手机上的进一步定位

新增 `files/last_export_diagnostic.json`，记录源尺寸、文件字节、格式、排队、读取、显影及编码、写相册、校验记录各阶段。原生结果细分 `set_params_ms`、`spectral_ms`、`edits_ms`、`encode_write_ms`。同时保留开始与结束的实际 GPU/CPU 模式、回退原因，以及失败所在阶段。关于页的“处理诊断 → 复制诊断”包含这份记录，存储于本机，不自动发送。

文件 MB 大小不能直接代表光谱显影计算量；需要按原图像素数量、效果和实际 GPU/CPU 模式判断。导出仍按原尺寸重新读取与显影。OPPO 的实测耗时和是否发生大图运行时回退尚未取得，不能从本机基准断言该手机已经达到相同速度。

## 最终应用流程补充

通过应用实际界面从系统文件管理器导入同一张 4000×3000 JPEG，在此前保留的 CPU 兼容模式、颗粒 1.6/光晕/炫光开启的状态下，实际写入相册共 50.823 秒，其中光谱显影 46.259 秒、调色 1.262 秒、编码缓存 1.076 秒、写相册 0.137 秒。输出仍为 4000×3000，17,888,548 字节。相册文件哈希与导出配方一致。这个流程与前述关闭效果且使用系统 GPU 的基准条件不同，不能混合对比。它说明兼容 CPU 的原尺寸光谱效果仍可能耗时较长，新的诊断能辨别这种情况；不能仅根据调色、编码优化就声称所有导出均已变快至八秒。
